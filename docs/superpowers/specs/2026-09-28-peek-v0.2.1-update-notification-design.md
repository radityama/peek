# Peek v0.2.1 — Update notification

## Goal and scope

Tell a person running a preview when a newer Peek release is available. The check is best effort: it cannot delay server discovery, tunnel creation, or LAN readiness; change Peek's exit status; or interrupt an active preview. It never installs a package. This work starts from `main` on `feat/v0.2.1-update-notification` and bumps the package and changelog to `0.2.1`. Publishing, an update command, and a JSON update event are outside this feature.

The notification applies to interactive `peek`, `peek dev`, and `peek --lan` sessions, including previews started with an explicit argv command. `peek doctor`, `peek doctor --live`, `--help`, and `--version` do not check for updates. `--json` skips the check entirely and keeps the existing newline-delimited JSON event contract. `CI=true`, `NODE_ENV=test`, and `NO_UPDATE_NOTIFIER=1` also skip the check before any cache or registry access. The environment variable is the explicit opt-out in this release; no new CLI flag is needed.

## Boundaries and data flow

An isolated `src/update` module accepts the installed package version, an abort signal, and injectable clock, cache, and HTTP operations. It returns either an available newer version or no result. It neither imports nor controls server discovery, process cleanup, LAN sharing, or the tunnel provider. The CLI starts the check after successful command validation without awaiting it. It continues ordinary startup immediately and owns the resulting notification state. `TerminalOutput` renders a concise update notice after a preview URL is shown. If the check completes first, the CLI holds the result until the initial ready callback; if it completes later, it prints then. It prints at most once per session, including tunnel reconnects. If no preview becomes ready or the lifecycle stops, it prints nothing and aborts an outstanding request. No update promise can become a top-level CLI error or an unhandled rejection.

The notice displays `Update available <installed> → <latest>` and `npm install --global @radityprtama/peek@latest`. It does not claim to know how Peek was originally installed. The module never sends the project name, path, dev server URL, tunnel URL, source files, or environment variables to npm. The sole registry request is a bounded HTTPS GET for the published `latest` version of `@radityprtama/peek`; the response is reduced to its `version` string. No telemetry or automatic installation is added.

## Cache and failure behavior

The cache lives at `~/.peek/update-check.json`, separate from any project, and contains only the last attempt time and, on success, the latest version. A valid successful record is reused for 24 hours without contacting npm. A failed attempt records its time but no candidate version; it also suppresses another request for 24 hours. An expired record triggers a new attempt. Invalid or corrupt cache content is ignored. Reads and writes use asynchronous filesystem operations, and writes replace the cache atomically. A short-lived cross-process claim prevents simultaneous Peek processes from starting duplicate requests against the same expired cache. A stale claim can be recovered after the bounded request deadline. If cache access fails, the update check quietly degrades; it cannot affect preview startup.

The registry request has a short timeout of about two seconds and is cancelled on lifecycle shutdown. Offline, DNS, HTTP, timeout, malformed-response, and cache failures are swallowed inside the update module. They produce no stack trace, warning, or changed exit code. A failed refresh does not display an expired cached result. These rules make the 24-hour interval best effort when the user's cache directory is unwritable, because Peek cannot persist a cooldown in that case.

Use npm's `latest` dist-tag rather than a list of all versions. Validate both version strings and compare them with the maintained `semver` package so equal or older published versions produce no notice. A stable installed version is never prompted to install a prerelease, even if a registry tag is misconfigured; an installed prerelease follows standard semver ordering. `semver` is the one new runtime dependency because prerelease comparison is easy to get wrong with a custom parser.

## Verification and documentation

Unit tests inject the clock, cache, and registry response. They cover equal, newer, older, and prerelease versions; a valid cache without a request; expiration after 24 hours; a failed attempt's 24-hour cooldown; corrupt cache; registry failure; timeout; and cancellation. Focused CLI tests verify interactive preview timing, one notice after ready even across reconnects, no notice before readiness, and no check for JSON, doctor, CI, test, or opt-out modes. Tests use fake processes and HTTP responses, never the public npm registry or Cloudflare network. A startup test holds the registry request open while proving that normal preview readiness is still emitted.

Document the automatic check, cache interval, opt-out, and update command in README and changelog; update package version and lockfile together. Run lint, typecheck, tests, build, `pnpm pack:check`, packed CLI smoke test, and inspect `npm pack --dry-run`. Keep the existing Node 22+ and platform CI coverage. Do not create a release tag or publish as part of this implementation unless separately requested.
